## Key Features

- Complete career assessments and review personal results.
- Explore and complete job simulations while tracking progress and outcomes.
- Use an AI career assistant to explore career options, retrieve authorized application data, and provide evidence-backed references.
- Use Admin Studio to manage Knowledge Bases, AI Agents, and AI Usage.
- Switch between Vietnamese and English throughout the interface.

## Running with Docker

### Requirements

- Git.
- Docker Desktop running with Linux containers.
- Docker Compose v2.17 or later.
- PowerShell on Windows.

Node.js and Java are not required when running the application entirely through Docker.

### 1. Clone the Repository

```powershell
git clone https://github.com/han-labs/career-simulation-platform.git
cd career-simulation-platform
```

### 2. Initialize the Local Configuration

```powershell
.\scripts\Initialize-LocalEnvironment.ps1
```

The script creates `.env` from `.env.example` if it does not already exist and generates a local JWT signing key.

Existing configuration and keys are preserved.

Edit your local `.env` file if required. Do not commit or share its contents.

### 3. Build and Start the Application

```powershell
docker compose -p careersimfresh up -d --build --wait
docker compose -p careersimfresh ps
```

Check backend health:

```powershell
Invoke-RestMethod http://localhost:8080/api/health
```

Open **http://localhost:8080** after the backend is ready.

| Area | Path |
|---|---|
| Sign in / Register | `/account` |
| Career Assessments | `/assessment` |
| Simulations | `/simulations` |
| Admin Studio | `/admin` |

Use the same `http://localhost:8080` origin throughout sign-in and application usage.

## Environment Variables

The list below contains configuration variable names only and does not include secret values.

| Group | Configuration Variables |
|---|---|
| PostgreSQL | `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_PORT` |
| JWT | `JWT_SIGNING_KEY`, `JWT_LIFETIME_SECONDS` |
| Local runtime | `SPRING_PROFILES_ACTIVE`, `LOCAL_DEMO_MODE` |
| Core features | `CORE_V2_ENABLED`, `VITE_CORE_V2_ENABLED` |
| Agent Platform | `AGENT_PLATFORM_ENABLED`, `VITE_AGENT_PLATFORM_ENABLED` |
| Gemini / embeddings | `GEMINI_API_KEY`, `GEMINI_MODEL`, `KNOWLEDGE_EMBEDDING_ENABLED` |
| OpenAI, if used | `OPENAI_API_KEY`, `AI_MODEL`, `AI_BASE_URL` |
| Google OAuth, if used | `GOOGLE_OAUTH_ENABLED`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `GOOGLE_REDIRECT_URI` |
| HTTP / frontend | `GATEWAY_PORT`, `BACKEND_PORT`, `FRONTEND_PORT`, `VITE_API_BASE_URL` |

Notes:

- The JWT signing key is generated by the initialization script; there is no need to copy a key from another developer.
- A new database should use its own PostgreSQL password before the first startup.
- An existing database must continue using connection settings compatible with its existing volume.
- Google OAuth and AI features require valid operator-provided configuration.
- Embeddings are not enabled by default in the template; configure a provider and enable the feature before using RAG.
- Do not place secrets in `VITE_*` variables because these values may be included in the frontend bundle.
- Keep `LOCAL_DEMO_MODE` disabled when testing real authentication and authorization behavior.

## Demo Data and Accounts

### Test Accounts

The following accounts are intended **only for the local demo database prepared by Group12**.

The repository does not automatically create these accounts when starting with a new database.

| Role | Email | Public Demo Password |
|---|---|---|
| Student | `student01@gmail.com` | `student123456` |
| Admin | `admin@gmail.com` | `admin1234567` |

Do not reuse these passwords for real accounts or publicly accessible environments.

For a new database:

- A Student account can be registered through `/account`.
- An Admin account must be provisioned by the team or an authorized operator using the appropriate process.
- Do not modify the database or bypass authorization controls to grant yourself Admin privileges.

### Career Assessments

The four local career assessments use a dedicated bootstrap process and are not automatically published by Flyway.

After the stack is ready, an operator can run:

```powershell
.\scripts\setup-us03-local.ps1 -EnableLocalBootstrap
```

This optional step requires **Java 17 and Node.js 22 on the host machine**.

The script uses the PostgreSQL instance from the `careersimfresh` project, can be executed repeatedly, and does not reset the database or modify `.env`.

### AI and Knowledge Bases

A new database does not contain Knowledge Bases, Agent configurations, conversation history, or personal results from another team member's machine.

A complete AI demonstration requires:

- A valid AI provider configuration.
- Documents processed and published in a Knowledge Base.
- An Agent configured, tested, and published for the appropriate role through the existing Agent workflow.

The application can still run its non-AI features without an AI API key.

## Updating and Operating the Application

Pull the latest source code, rebuild, and apply changes:

```powershell
git pull --ff-only origin main
docker compose -p careersimfresh up -d --build --wait
```

View service status and backend logs:

```powershell
docker compose -p careersimfresh ps
docker compose -p careersimfresh logs --tail=100 backend
```

Stop and restart the application while preserving data:

```powershell
docker compose -p careersimfresh stop
docker compose -p careersimfresh up -d --wait
```

The frontend and backend run from Docker images, so source-code changes require a rebuild.

Flyway migrations run automatically when the backend starts.

**Do not delete volumes, run `down -v`, or execute Flyway clean/repair during normal development or operation.**

PostgreSQL data and uploaded documents are stored in persistent volumes.

## Security

- Do not commit `.env`, API keys, JWT signing keys, OAuth secrets, tokens, or database dumps containing private data.
- Do not include real credentials in issues, screenshots, or public logs.
- Demo accounts must only be used with synthetic data in an isolated local environment.
- The local Docker configuration is not intended to be used directly as an Internet-facing production deployment.
- Cloning or forking the repository does not grant permission to push to the original repository.
