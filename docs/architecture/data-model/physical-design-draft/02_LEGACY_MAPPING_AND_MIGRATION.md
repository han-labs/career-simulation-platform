## 2. Migration architecture decision

| Option | Advantages | Costs/risk |
|---|---|---|
| Additive tables in existing public schema — **selected** | Reuses identity IDs/FKs, same transaction manager and Flyway history; little search_path/JPA change; easiest for two students | Transitional singular/plural pairs require explicit mappings and ownership tests; table count increases during coexistence |
| Separate `careersim_v3` schema | Clear namespace and grants; duplicate names possible | Cross-schema FKs or copied identity, JPA/JDBC schema qualifications, two sets of grants/search-path risks, no automatic tenant isolation; same DB rollback complexity |

New table names in 01 are deliberate and must not be pluralized into existing names. Map new JPA classes with explicit `@Table(name=..., schema="public")`; use `VersionedAssessmentAttempt`/`ScenarioTask`/`EnrollmentTaskSubmission` class names where existing legacy names conflict. JDBC uses schema-qualified table names for new SQL. Existing plural-table entities remain legacy adapters. Do not make unverified broad find/replace changes. Runtime application role has no DDL; Flyway migrator owns schema. No separate database per module, no tenant-specific schemas.

## 4. Historical preservation and namespace strategy

New references use typed namespaces: `ASSESSMENT:<new-id>:<version-id>`, `SUBMISSION:<id>:<version-id>`, `COMPLETION:<id>`, `KNOWLEDGE:<chunk-id>:<document-version-id>`. Existing A/S/K references remain legacy references. Client DTOs include sourceKind/version rather than infer meaning from an overlapping integer. v1 K inspector routes only legacy K IDs; v2 inspector routes new references. No source record is deleted, renumbered or assigned invented content provenance.

Prefer **read-through compatibility, no dual business writes**. During expansion old app writes legacy only; v2 routes are not publicly enabled. At cutover, quiesce old writes, record snapshot hashes/watermark, enable new authority. Old attempts/results remain accessible through owner-authorized legacy reads. Historical in-progress work remains readable/exportable with an explicit explanation and a user action to start a new version; do not silently discard browser draft state. Current catalog can stay legacy read-only until reviewed new content exists. A failed frontend request or locally evaluated score is never a database record.

Application feature switches: `core-v2-enabled`, `legacy-write-enabled`, `agent-v2-enabled`. Production combinations must never allow new content via legacy grading writes. Once core-v2 cutover, legacy-write-enabled=false; immutable history adapters remain. Rollout switches are operational configuration, not a new database feature-flag table. Authentication tightening applies to both v1/v2 before any public deployment.

4. **CUTOVER:** deploy authenticated backend and coordinated frontend compatibility changes; drain pending legacy turns within their deadline, block legacy submissions, take final watermark; route new sessions/attempts/enrollments to new stores; verify owner/status/tenant enforcement and all core flows with AI disabled. 5. **CONTRACT:** remove old write capability from application and runtime DB role where feasible without breaking retained reads; retire obsolete services only after caller inventory proves none remain. Keep history and V1–V14. Table drops, consent deletion and legacy retention cleanup need an approved retention/data-loss plan, outside this implementation.

### Rollback/restore

Additive DDL rollback is usually a forward-fix; do not down-migrate tables containing new evidence. Before cutover, old binary can continue against untouched legacy tables after verified compatibility. After new writes begin, reverting all traffic to legacy cannot represent new submissions/completions/configs; keep new reads available and disable affected writes while forward-fixing. If restore is necessary, obtain explicit owner authorization and agree recovery point/data reconciliation first. Preserve post-backup new records before restoration; no promise of zero loss without rehearsal. Disabling a provider or agent never blocks core submission/completion.
