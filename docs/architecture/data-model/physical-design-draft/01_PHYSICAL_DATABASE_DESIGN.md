# CareerSim physical database design — proposal for approval

Status: **PROPOSED DESIGN**, 2026-10-14. No DDL has been executed. Read with documents 02–04 in this directory. The user's supplied architecture request is the approved business baseline; approval of this physical design is still pending.

## 1. Decisions and inventory

Use one PostgreSQL 17 database and the existing `public` schema. Preserve the 21 existing tables; retain four as active shared foundations and introduce **40 new tables**, including one temporary migration ledger. End-of-cutover inventory: **44 active tables + 17 preserved legacy tables = 61 physical tables**, excluding Flyway/framework internals. This is a coexistence count, not 61 new domain entities. No automatic removal is planned.

Keep `app_users`, `student_profiles`, `career_path_profiles`, and `learning_resources`. New tables use singular names to avoid collisions with existing plural names. Keep legacy BIGINT IDs; new business IDs use `bigint GENERATED BY DEFAULT AS IDENTITY`. Conversation, run and proposal IDs use application-generated UUIDs for retry/correlation. IDs are not authorization. New API BIGINT IDs are decimal strings; legacy DTO numeric IDs stay unchanged within their existing range. No UUID conversion of legacy records.

| Module | Active tables | Why they persist |
|---|---|---|
| identity | app_users, student_profiles, consent_grant | Account/profile separation; independently revocable purpose grants |
| enterprise | enterprise, enterprise_representative | Organization identity differs from login; one membership per representative |
| assessment | assessment_type, assessment_version, assessment_question, assessment_attempt, assessment_response, assessment_result | Versioned content, unlimited retakes, answer-level provenance and deterministic results |
| simulation (authoring) | scenario, scenario_version, simulation_task, task_deliverable_definition, task_resource, model_answer, career_skill, task_skill | Immutable task content and relational membership of resources/deliverables/skills |
| simulation (participation) | simulation_enrollment, task_submission, submitted_deliverable, simulation_completion | Version pin, one final task submission, multiple payloads, completion artifact |
| guidance | exploration_plan, career_path_profiles, learning_resources | Confirmed plans and reusable reviewed guidance catalogs |
| agent | agent, agent_configuration, agent_configuration_kb, agent_conversation, agent_message, agent_run, agent_run_consent, agent_memory, agent_action_proposal | Configuration provenance, explicit KB grants, durable execution, consent lineage, reviewed memory, approval lifecycle |
| knowledge | knowledge_base, knowledge_document, knowledge_document_version, knowledge_chunk, embedding_profile, knowledge_chunk_embedding | KB isolation, staged publication and profile-compatible embeddings |
| common infrastructure | file_asset, audit_event | Protected blobs and minimized operational accountability |
| migration-only | migration_record | Restartable, reviewed mapping/conflict evidence; not product history |

No separate certificate, resume-snippet, practiced-skill evidence, dashboard, evaluator, tool-registry, provider-secret, AdminProfile or generic workflow table. Certificate/snippet are fixed completion values; practiced skills are a query over final submissions and immutable task_skill; tools/evaluators are typed code registries. JSONB is for validated bounded value objects, not FK lists or authorization relationships.

## 2. Dictionary notation (normative)

Each field below gives physical name, PostgreSQL type, nullability and default. `!` = NOT NULL; `?` = NULL allowed, default NULL. Omitted defaults for `!` fields mean **no default**, caller must supply. `id: ID` expands to `id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`; `UUID` expands to `uuid !` with **no SQL default**, generated once by the caller. `PK`, `U`, `FK`, `C`, and `I` denote primary key, unique constraint, foreign key, CHECK and extra index. References without a target column mean `(id)`. Every FK is **ON DELETE RESTRICT, ON UPDATE RESTRICT**, immediate, unless explicitly overridden. There are no implicit cascades.

`created_at: TS` expands to `timestamptz ! DEFAULT CURRENT_TIMESTAMP`; `updated_at: TS` has the same default, explicitly updated by the application, never assumed automatic. `row_version: RV` = `bigint ! DEFAULT 0 CHECK(row_version >= 0)`, incremented for every mutable aggregate update. These are explicitly listed where present; there are no hidden columns. `hash` means `varchar(64)` with CHECK matching `^[0-9a-f]{64}$`. All JSONB object/array fields have `jsonb_typeof` CHECKs as indicated; application validates their versioned schema and size. Enumerations listed in braces are `varchar(32)` + CHECK, not PostgreSQL enum types.

Index rule applicable to **every** table: PK/U already create B-tree indexes; add a nonunique B-tree on each FK column tuple unless an existing PK/U/I has that tuple as a leading prefix. Skip a redundant single-column FK index where the leading compound FK index suffices. Purpose: reference checks and owner-scoped reads. Additional workload indexes are explicitly listed below. No blanket indexes on all statuses/JSONB. New table/constraint names must be unique within the schema; use `pk_<table>`, `uq_<table>_<meaning>`, `fk_<table>_<parent>_<meaning>`, `ck_<table>_<meaning>`.

Lifecycle codes used below: **M** mutable aggregate with optimistic version and transaction authorization; **V** draft editable, published payload immutable, withdrawal handled at root/access policy; **H** historical append/finalize, no product hard delete; **O** operational lifecycle with bounded redaction; **J** association governed by parent lifecycle. Cross-row invariants are not fake CHECKs: use composite FKs where possible and the transactions in §8 elsewhere. PostgreSQL documents these constraint boundaries and null behavior in its [PostgreSQL 17 constraint reference](https://www.postgresql.org/docs/17/ddl-constraints.html).

## 3. Identity, enterprise, consent and infrastructure

### 3.1 app_users — identity, M; retained/extended

`id bigint PK` retains BIGSERIAL default; `email varchar(255) !`; `password_hash varchar(255) !`; `display_name varchar(150) !`; `role varchar(30) ! {STUDENT,ENTERPRISE,ADMINISTRATOR}`; `status varchar(30) ! DEFAULT 'ACTIVE' {ACTIVE,INACTIVE,LOCKED}`; `created_at TS`; `updated_at TS`; **add** `row_version RV`, `privacy_version bigint ! DEFAULT 0 CHECK >= 0`.

Preserve existing U(email). Add unique index `lower(btrim(email))` only after collision preflight. Store new emails trimmed/lowercase. Preserve legacy spelling until a reviewed normalization operation. Domain/API `ADMIN` maps explicitly to storage `ADMINISTRATOR`; never a fourth role. Account disable, credential change, membership/consent changes invalidate effective authorization. Privacy version increments on consent grant/revoke and memory disable/clear. No account hard-delete endpoint. Demo credentials do not become production credentials.

### 3.2 student_profiles — identity, M; retained/extended

`user_id bigint PK FK app_users`; `school_name varchar(255) ?`; `education_level varchar(80) ?`; `graduation_year smallint ?`; `consented_to_ai_at timestamptz ?` **legacy only, never new authority**; `created_at TS`; `updated_at TS`; **add** `major varchar(160) ?`, `career_goal text ?`, `declared_interests jsonb ! DEFAULT '[]'` array, `row_version RV`.

No second profile identity: domain student ID = account ID. Identity service enforces STUDENT role and creates profile with registration transaction; profile absence blocks student operations, not consent bypass. Existing invalid role/profile rows are reported before correction.

### 3.3 enterprise — enterprise, M

`id ID`; `name varchar(240) !`; `verification_status {PENDING,VERIFIED,REJECTED} ! DEFAULT 'PENDING'`; `publishing_status {DISABLED,ENABLED,SUSPENDED} ! DEFAULT 'DISABLED'`; `created_at TS`; `updated_at TS`; `row_version RV`.

C nonblank name. No uniqueness on name (names are not organizational identity). Registration creates PENDING/DISABLED. Admin verification does not automatically enable publication. Proposed publication policy requires VERIFIED + ENABLED; see approval decisions in 03.

### 3.4 enterprise_representative — enterprise, M

`user_id bigint PK FK app_users`; `enterprise_id bigint ! FK enterprise`; `membership_status {ACTIVE,SUSPENDED} ! DEFAULT 'ACTIVE'`; `publishing_permission boolean ! DEFAULT false`; `created_at TS`; `updated_at TS`; `row_version RV`.

One account has exactly one enterprise when membership exists; many accounts may share enterprise. Application verifies ENTERPRISE role. Moving an existing membership to another tenant is **not** an ordinary edit; disable and explicitly review transfer after invalidating sessions/context. No self-grant of publishing permission.

### 3.5 consent_grant — identity, H

`id ID`; `user_id bigint ! FK app_users`; `purpose {PROFILE_SHARE,COMPLETION_SHARE,SUBMISSION_SHARE,ASSESSMENT_SHARE,EXTERNAL_AI,LONG_TERM_MEMORY,RECRUITMENT_CONTACT} !`; `enterprise_id bigint ? FK enterprise`; `recipient_key varchar(180) !`; `policy_version varchar(80) !`; `confirmed_at timestamptz !`; `revoked_at timestamptz ?`; `expires_at timestamptz ?`; `confirmation_method {EXPLICIT_UI} !`; `created_at TS`.

U(id,user_id). Partial U(user_id,purpose,recipient_key) WHERE revoked_at IS NULL; expire by setting revoked_at before a new grant, preserving expires_at. C revoked_at/ expires_at each NULL or >= confirmed_at. C enterprise purposes PROFILE_SHARE/COMPLETION_SHARE/SUBMISSION_SHARE/ASSESSMENT_SHARE/RECRUITMENT_CONTACT require enterprise_id and `recipient_key='enterprise:' || enterprise_id::text`; other purposes require enterprise_id NULL. EXTERNAL_AI recipient `provider:<registered-provider-code>` validated against code registry; LONG_TERM_MEMORY recipient exactly `platform-memory`. I(user_id,purpose,confirmed_at DESC). Status is derived from timestamps; no redundant status column. A new grant is a new row; revocation never turns an old grant on again. Explicitly confirmed UI event required; preselected UI state and legacy timestamp are insufficient. Recruitment scope is reserved, no recruitment endpoints implemented.

### 3.6 file_asset — common storage, O

`id ID`; `owner_user_id bigint ! FK app_users`; `enterprise_id bigint ? FK enterprise`; `storage_key varchar(512) ! U`; `original_name varchar(255) !`; `mime_type varchar(120) !`; `size_bytes bigint ! CHECK >= 0`; `checksum hash !`; `state {STAGED,READY,REJECTED,REDACTED} ! DEFAULT 'STAGED'`; `created_at TS`; `ready_at timestamptz ?`; `row_version RV`.

C state != READY OR ready_at IS NOT NULL (REDACTED may preserve its earlier ready_at). Service validates bytes, MIME, size, checksum and uploader/context. Private storage only; storage_key never a public URL. Association-specific authorization at every download. A student may attach only own READY files, an author only own-tenant files. Finalized/published references pin bytes. Redaction is an exceptional approved privacy operation preserving metadata, never silent replacement.

### 3.7 audit_event — common audit, H

`id ID`; `actor_user_id bigint ? FK app_users`; `action varchar(100) !`; `target_type varchar(80) !`; `target_key varchar(100) !`; `detail jsonb ! DEFAULT '{}'` object; `occurred_at timestamptz ! DEFAULT CURRENT_TIMESTAMP`; `correlation_id uuid ?`.

I(target_type,target_key,occurred_at); I(actor_user_id,occurred_at DESC). System actions permit NULL actor. Target key is a diagnostic string, intentionally not a polymorphic FK and never an authorization fact. Store hashes/status/IDs/reason codes, not passwords, tokens, submission text, prompts or chain of thought. Critical authorization/publication/approval audits commit with business action. Retention policy pending approval; no automatic history purge.

### 3.8 migration_record — system migration, O

`id ID`; `source_table varchar(80) !`; `source_key varchar(180) !`; `target_table varchar(80) ?`; `target_key varchar(180) ?`; `source_hash hash !`; `state {PENDING,MAPPED,PRESERVED,CONFLICT} !`; `reason_code varchar(100) !`; `reviewed_by bigint ? FK app_users`; `reviewed_at timestamptz ?`; `details jsonb ! DEFAULT '{}'` object; `updated_at TS`.

U(source_table,source_key). C target_table and target_key both NULL or both non-NULL; MAPPED requires both. I(state,id). Keys include composite legacy keys canonically, e.g. `attempt:question`. Target references are deliberately diagnostic; backfill validates target existence before marking MAPPED. No universal runtime DAO may use this ledger to bypass real FKs. No copied sensitive row payloads. Removal deferred until independent preservation/reconciliation evidence exists.

## 4. Assessment

### 4.1 assessment_type — assessment, M

`id ID`; `code varchar(80) ! U`; `name varchar(160) !`; `status {ACTIVE,ARCHIVED} ! DEFAULT 'ACTIVE'`; `active_version_id bigint ?`; `created_at TS`; `row_version RV`.

FK(id,active_version_id) -> assessment_version(assessment_type_id,id), added after version table. NULL pointer initially; set only to published version of this type. No single global assessment version. Type archive blocks new attempts, not owned history reads.

### 4.2 assessment_version — assessment, V

`id ID`; `assessment_type_id bigint ! FK assessment_type`; `version_number integer ! CHECK > 0`; `status {DRAFT,PUBLISHED} ! DEFAULT 'DRAFT'`; `evaluator_key varchar(100) !`; `evaluator_version varchar(80) !`; `scoring_config jsonb !` object; `content_hash hash ?`; `created_at TS`; `published_at timestamptz ?`; `row_version RV`.

U(assessment_type_id,version_number); U(assessment_type_id,id); C DRAFT => published_at NULL, PUBLISHED => published_at/content_hash non-NULL. Publish validates all questions and frozen evaluator contract. Do not alter evaluator code under the same evaluator_version. Immutable data after publication, including translations/scoring config.

### 4.3 assessment_question — assessment, V/J

`id ID`; `assessment_version_id bigint ! FK assessment_version`; `position integer ! CHECK > 0`; `prompt text !`; `response_type {LIKERT,CHOICE,TEXT} !`; `response_config jsonb !` object; `translations jsonb ! DEFAULT '{}'` object; `required boolean ! DEFAULT true`.

U(assessment_version_id,position); U(id,assessment_version_id). Response config has schemaVersion plus bounds/options and evaluator dimension where relevant. Current RIASEC is LIKERT 1–5 with dimension R/I/A/S/E/C. No active flag allowing questions to change during an attempt. Additional assessment types require a registered deterministic evaluator; unsupported evaluator cannot publish.

### 4.4 assessment_attempt — assessment, H

`id ID`; `student_id bigint ! FK student_profiles(user_id)`; `assessment_version_id bigint ! FK assessment_version`; `status {IN_PROGRESS,SUBMITTED} ! DEFAULT 'IN_PROGRESS'`; `start_request_id uuid !`; `started_at timestamptz ! DEFAULT CURRENT_TIMESTAMP`; `submitted_at timestamptz ?`; `final_payload_hash hash ?`; `row_version RV`.

U(student_id,start_request_id); U(id,assessment_version_id). C SUBMITTED requires submitted_at/hash; IN_PROGRESS requires both NULL. I(student_id,started_at DESC,id). **No U(student_id,assessment_version_id)**: retakes unlimited. Same start_request_id/version replays; same request ID with another version conflicts. Version FK plus service publication gate.

### 4.5 assessment_response — assessment, H/J

`attempt_id bigint !`; `question_id bigint !`; `assessment_version_id bigint !`; `answer_data jsonb !` object; `updated_at TS`.

PK(attempt_id,question_id). FK(attempt_id,assessment_version_id) -> assessment_attempt(id,assessment_version_id). FK(question_id,assessment_version_id) -> assessment_question(id,assessment_version_id). Mutable only while attempt IN_PROGRESS, validated by frozen response config. Submission validation compares exact distinct required question IDs; duplicate request entries fail before upsert/scoring.

### 4.6 assessment_result — assessment, H

`attempt_id bigint PK FK assessment_attempt`; `result_data jsonb !` object; `evaluator_key varchar(100) !`; `evaluator_version varchar(80) !`; `input_hash hash !`; `calculated_at timestamptz ! DEFAULT CURRENT_TIMESTAMP`.

One result per attempt, inserted atomically with SUBMITTED transition. JSON schema carries schemaVersion, assessment type/version, dimension codes, raw values, scales and deterministic interpretation codes; no unconstrained AI interpretation. Evaluator key/version must equal pinned version at calculation. No weighted cross-type composite score without a separate approved methodology. Recompute as verification only, never overwrite historical result.

## 5. Scenario content and learning participation

### 5.1 scenario — simulation, M

`id ID`; `enterprise_id bigint ! FK enterprise`; `slug varchar(120) ! U`; `availability_status {AVAILABLE,ARCHIVED,SUSPENDED} ! DEFAULT 'ARCHIVED'`; `current_version_id bigint ?`; `created_at TS`; `updated_at TS`; `row_version RV`.

FK(id,current_version_id) -> scenario_version(scenario_id,id). I(enterprise_id,availability_status,id). Owner enterprise immutable after first publication. AVAILABLE needs a published pointer (application). ARCHIVED hides new enrollment while allowing pinned existing work; SUSPENDED blocks protected content access for safety until explicit resolution. Neither rewrites or deletes evidence.

### 5.2 scenario_version — simulation, V

`id ID`; `scenario_id bigint ! FK scenario`; `version_number integer ! CHECK > 0`; `status {DRAFT,PUBLISHED} ! DEFAULT 'DRAFT'`; `title varchar(180) !`; `target_role varchar(120) !`; `career_track varchar(60) !`; `summary varchar(600) !`; `introduction text !`; `learning_objectives text !`; `difficulty varchar(30) ! {INTRODUCTORY,INTERMEDIATE,ADVANCED}`; `estimated_minutes integer ! CHECK > 0`; `translations jsonb ! DEFAULT '{}'` object; `provenance jsonb !` object; `content_hash hash ?`; `created_at TS`; `published_at timestamptz ?`; `row_version RV`.

U(scenario_id,version_number); U(scenario_id,id). Publication timestamp/hash CHECK as assessment_version. Provenance records original/licensed origin, reviewer and review time; application requires real review at publish. All metadata used by history is in the version, not mutable root. Publication requires at least one required task and a deliverable for each task; this avoids zero-work completion. This is a proposed content validation default, not an inferred old rule.

### 5.3 simulation_task — simulation, V/J

`id ID`; `scenario_version_id bigint ! FK scenario_version`; `position integer ! CHECK > 0`; `title varchar(180) !`; `workplace_context text !`; `instructions text !`; `required boolean ! DEFAULT true`; `translations jsonb ! DEFAULT '{}'` object.

U(scenario_version_id,position); U(id,scenario_version_id). No score, max_score or evaluation_rule in new tasks. Parent version controls mutability. Task order is presentation; no prerequisite lock unless separately approved.

### 5.4 task_deliverable_definition — simulation, V/J

`id ID`; `task_id bigint ! FK simulation_task`; `position integer ! CHECK > 0`; `name varchar(180) !`; `format {TEXT,URL,FILE,JSON} !`; `required boolean ! DEFAULT true`; `validation_config jsonb !` object.

U(task_id,position); U(id,task_id). Validation config is format-dependent, versioned and bounded (length, MIME/size, HTTPS, JSON schema/options). Validate structure/completeness, not professional competence. Missing optional items allowed; supplied optional items must validate too. Every published task must have at least one required deliverable.

### 5.5 task_resource — simulation, V/J

`id ID`; `task_id bigint ! FK simulation_task`; `position integer ! CHECK > 0`; `title varchar(180) !`; `file_asset_id bigint ? FK file_asset`; `external_url varchar(2000) ?`; `release_policy {TASK_ACCESS,AFTER_SUBMISSION} ! DEFAULT 'TASK_ACCESS'`.

U(task_id,position); C num_nonnulls(file_asset_id,external_url)=1. AFTER_SUBMISSION resources include model-answer attachments, preserving actual FKs rather than JSON asset lists. External URLs are references, never backend-fetch commands; HTTPS/host policy in service. Never put a private answer on an unprotected external URL.

### 5.6 model_answer — simulation, V/J

`task_id bigint PK FK simulation_task`; `content text !`; `translations jsonb ! DEFAULT '{}'` object; `release_policy {AFTER_VALID_SUBMISSION} ! DEFAULT 'AFTER_VALID_SUBMISSION'`.

One model answer per task, immutable with version. Student must own a FINAL valid submission for that exact task/version. Owning author may review draft/published authored answers through authoring API. Detailed submission sharing does not independently grant model-answer access. No public entity serialization.

### 5.7 career_skill — simulation vocabulary, M

`id ID`; `code varchar(80) ! U`; `name varchar(160) !`; `status {ACTIVE,ARCHIVED} ! DEFAULT 'ACTIVE'`; `created_at TS`; `row_version RV`.

Codes stable; rename changes display vocabulary, not claims about skill attainment. Archived skills remain on historical tasks. Human review resolves conflicting legacy names/codes; no AI inference from free text.

### 5.8 task_skill — simulation, V/J

`task_id bigint ! FK simulation_task`; `skill_id bigint ! FK career_skill`; `skill_name_snapshot varchar(160) !`; PK(task_id,skill_id).

Immutable after parent publication. Snapshot preserves historical display labels while vocabulary can evolve. Evidence query joins this association to FINAL task_submission, enrollment and student, returning submission/task/version IDs and submitted_at. Completion is not required to show already-practiced tasks; draft work never counts.

### 5.9 simulation_enrollment — simulation, H

`id ID`; `student_id bigint ! FK student_profiles(user_id)`; `scenario_version_id bigint ! FK scenario_version`; `status {ENROLLED,IN_PROGRESS,COMPLETED} ! DEFAULT 'ENROLLED'`; `enrolled_at timestamptz ! DEFAULT CURRENT_TIMESTAMP`; `started_at timestamptz ?`; `completed_at timestamptz ?`; `row_version RV`.

U(student_id,scenario_version_id); U(id,scenario_version_id). I(student_id,enrolled_at DESC,id). C completed_at non-NULL iff COMPLETED; started_at required for IN_PROGRESS/COMPLETED. One row per student/version forever. POST enrollment naturally idempotent under U. Distinct versions of same scenario may be active concurrently. No assessment FK/prerequisite. Existing enrollment pins version forever.

### 5.10 task_submission — simulation, H

`id ID`; `enrollment_id bigint !`; `task_id bigint !`; `scenario_version_id bigint !`; `status {DRAFT,FINAL} ! DEFAULT 'DRAFT'`; `final_request_id uuid ?`; `final_payload_hash hash ?`; `created_at TS`; `submitted_at timestamptz ?`; `row_version RV`.

FK(enrollment_id,scenario_version_id) -> simulation_enrollment(id,scenario_version_id); FK(task_id,scenario_version_id) -> simulation_task(id,scenario_version_id). U(enrollment_id,task_id), including draft. U(id,task_id). Partial U(enrollment_id,final_request_id) WHERE final_request_id IS NOT NULL. C FINAL requires all three final_request_id/hash/submitted_at; DRAFT requires all NULL. Same request ID/hash replays; changed payload or new submission after FINAL returns conflict. No second row on resubmit.

### 5.11 submitted_deliverable — simulation, H/J

`submission_id bigint !`; `definition_id bigint !`; `task_id bigint !`; `content_text text ?`; `content_url varchar(2000) ?`; `file_asset_id bigint ? FK file_asset`; `content_json jsonb ?` object when present; `updated_at TS`.

PK(submission_id,definition_id). FK(submission_id,task_id) -> task_submission(id,task_id). FK(definition_id,task_id) -> task_deliverable_definition(id,task_id). C num_nonnulls(content_text,content_url,file_asset_id,content_json)=1. Service additionally checks matching definition format and READY asset ownership. Rows editable/removable only before finalization. JSON is a fourth payload alternative to support original choice/ordering exercises without introducing grading or a table for each format.

### 5.12 simulation_completion — simulation evidence, H

`id ID`; `enrollment_id bigint ! U FK simulation_enrollment`; `completed_at timestamptz !`; `resume_snippet_text text !`; `snippet_template_version varchar(80) !`; `certificate_code varchar(80) ! U`; `certificate_snapshot jsonb !` object; `certificate_issued_at timestamptz !`.

Inserted once with last required task's finalization transaction. All columns immutable. Completion has no score/grade. Snapshot includes student display name, scenario/version title, enterprise name, completed date, issuer and completion-only disclaimer; no claims of competence. Fixed deterministic snippet generated once from completed required tasks and immutable skill labels. Certificate is data rendered on demand, not a stored binary or separate issuance workflow. Certificate reads require authorization; no public name lookup. If later binary export fails, completion already exists and rendering retries safely.

## 6. Guidance and agent platform

### 6.1 exploration_plan — guidance, M/H

`id ID`; `student_id bigint ! FK student_profiles(user_id)`; `source_proposal_id uuid ? U FK agent_action_proposal`; `title varchar(120) !`; `steps jsonb !` array; `status {ACTIVE,ARCHIVED} ! DEFAULT 'ACTIVE'`; `confirmed_at timestamptz !`; `row_version RV`.

Partial U(student_id) WHERE status='ACTIVE'. I(student_id,confirmed_at DESC,id). One current plan, retain archived confirmations. Direct user confirmation has NULL source proposal; agent proposal execution links exact proposal. Steps = 1–5 bounded strings (240 chars each), no invented autonomous plan execution. Replacing current plan archives it in same transaction. Source proposal FK added after agent tables; core direct plan works before Agent platform installation.

### 6.2 career_path_profiles — guidance, retained M

`code varchar(60) PK`; `title varchar(120) !`; `summary varchar(500) !`; `riasec_codes varchar(12) !`; `typical_activities jsonb !` array; `skill_codes jsonb !` array; `status varchar(20) ! {ACTIVE,ARCHIVED}`. No defaults. Retain current shape. Add array shape checks after preflight. References in skill_codes remain advisory reviewed labels, not practiced evidence; no invented FK to certify skills. New content reviewed by admin.

### 6.3 learning_resources — guidance, retained M

`id bigint PK` retains BIGSERIAL; `title varchar(180) !`; `provider varchar(100) !`; `url varchar(500) ! U`; `skill_code varchar(80) !`; `career_track varchar(60) !`; `difficulty varchar(30) !`; `estimated_minutes integer ! CHECK > 0`; `resource_type varchar(40) !`; `status varchar(20) ! {REVIEWED,ARCHIVED}`; `reviewed_at timestamptz !`. No defaults. I(status,career_track,skill_code) only if catalog filter plan benefits; otherwise defer. These reviewed resource facts are separate from generated/live-web sources; no automatic promotion.

### 6.4 agent — agent, M

`id ID`; `code varchar(80) ! U`; `name varchar(160) !`; `status {ACTIVE,DISABLED} ! DEFAULT 'DISABLED'`; `current_configuration_id bigint ?`; `created_at TS`; `row_version RV`.

FK(id,current_configuration_id) -> agent_configuration(agent_id,id). Admin-created registry entries; Syn and Enterprise Assistant are seed configurations. Disabling an agent revokes all future runs even for pinned old conversations. Runtime audience policy is versioned on configuration, not a mutable JSON grant on Agent.

### 6.5 agent_configuration — agent, V

`id ID`; `agent_id bigint ! FK agent`; `version_number integer ! CHECK > 0`; `status {DRAFT,PUBLISHED,REVOKED} ! DEFAULT 'DRAFT'`; `policy_key varchar(80) !`; `provider_key varchar(80) !`; `model_key varchar(160) !`; `instructions text !`; `allowed_roles text[] ! DEFAULT '{}'`; `enabled_tools text[] ! DEFAULT '{}'`; `execution_limits jsonb !` object; `memory_policy jsonb !` object; `content_hash hash ?`; `created_by bigint ! FK app_users`; `created_at TS`; `published_at timestamptz ?`; `row_version RV`.

U(agent_id,version_number); U(agent_id,id). C allowed_roles subset of ARRAY['STUDENT','ENTERPRISE','ADMIN']; no NULL array items. Same no-NULL rule for enabled_tools. DRAFT has no published_at, PUBLISHED/REVOKED require timestamp/hash. Publish requires at least one role, valid registered tools/provider/policy and bounded settings. REVOKED is a monotonic runtime permission override, not payload editing. Tool catalog is code; unknown names rejected. New config starts with zero grants. Config editing creates a new version; conversations never silently switch.

### 6.6 agent_configuration_kb — agent, J

### 7.5 embedding_profile — knowledge, immutable registration

`id ID`; `profile_key varchar(180) ! U`; `provider_key varchar(80) !`; `model_key varchar(160) !`; `dimensions integer ! CHECK BETWEEN 1 AND 16000`; `distance_metric {COSINE} ! ### 7.6 knowledge_chunk_embedding — knowledge, V/J

`chunk_id bigint ! FK knowledge_chunk`; `embedding_profile_id bigint !`; `dimensions integer !`; `embedding vector !`; `created_at TS`.

PK(chunk_id,embedding_profile_id). FK(embedding_profile_id,dimensions) -> embedding_profile(id,dimensions). C vector_dims(embedding)=dimensions; C vector_norm(embedding)>0. Provider adapter rejects nonfinite values and wrong response counts. Start with exact search scoped to one full profile per vector query. Scope rows first in a materialized eligible CTE/subquery so mixed dimensions never reach the distance operator; validate query dimensions. Existing legacy `vector(768)` stays unchanged. Variable-dimension storage and profile-specific partial expression indexes are supported by [pgvector's official guidance](https://github.com/pgvector/pgvector#can-i-store-vectors-with-different-dimensions-in-the-same-column). ANN indexes deferred until measured; any future index/query uses one profile and explicit fixed-dimension cast. Same dimensions do not imply compatible embeddings.

One document may have multiple complete embedding profiles. Enable a profile for retrieval only when every currently active chunk has its embedding for that profile; otherwise lexical-only for that document/profile, never silently mix spaces. Agent execution_limits chooses supported retrieval profile keys, validated at configuration publish. Multiple-KB search applies the same authorization predicate to vector and lexical paths, merges bounded ranked IDs using RRF, then records actual delivered chunks in run provenance.

## 8. Invariant enforcement and transaction contracts

| Invariant | Declarative database protection | Transactional/application protection |
|---|---|---|
| One account role/enterprise membership | role CHECK; representative user PK | role/profile/membership consistency; current status and tenant |
| Version-consistent answers | composite response FKs | published version start; duplicate/missing/invalid answers; immutable evaluator |
| Same task/version submission | two composite task_submission FKs | lock enrollment then submission; draft/final transitions |
| Deliverable belongs to task | submitted_deliverable composite FKs; one payload CHECK | matching format, full required set, ready owned assets |
| One final only | U(enrollment,task), final state CHECK | reject edits to FINAL and its children; same-key/hash replay |
| Completion | U(enrollment) | all required tasks FINAL in pinned version; one transaction with final submission |
| Fixed snippet/certificate | completion unique keys | insert once, no update route; immutable template snapshot |
| Config provenance | conversation/config and run/owner/config FKs | publish freeze, agent/config revocation, per-tool live checks |
| Consent provenance | run-consent and memory-owner composite FKs | purpose/recipient/effective timestamp checks, serialized revocation |
| KB isolation | KB owner FK/check; explicit config-KB junction | actor/config/tenant intersection for search and source inspection |
| Approved writes | target FKs, proposal lifecycle checks | payload hash + approval + current auth + expected revision atomically |

Implement DB trigger guards (defense in depth) for published assessment/scenario child payload mutations, published configuration payload/junction mutations, FINAL submission child mutations and completion/result updates/deletes. A child-mutation guard must **lock parent** before checking state; publisher/finalizer uses same parent lock, avoiding check-then-publish races. Allow draft edits and designated operational state/metadata updates only. No ORM cascade REMOVE for historical aggregates. Tests attempt direct SQL violations as well as service races. These guards are not substitutes for business services.

READ COMMITTED + explicit locks is the default. Lock order: relevant user accounts (sorted IDs) -> enterprise/membership -> owning aggregate root -> child rows (sorted IDs) -> completion/proposal-related target writes. Proposal execution first obtains actor and target aggregate locks, then proposal lock; every competing approve/execute follows this order. Knowledge publication locks document; search finalization locks referenced document/KB permission roots in ascending IDs for final authorization. Avoid long DB transactions during file upload, parsing, embedding or LLM calls.

Required-task finalization transaction: authenticate actor; lock enrollment; get/create unique draft; lock submission; if already FINAL, return the recorded result only for the same final_request_id and payload hash after current authorization, otherwise conflict. Only a still-DRAFT submission checks If-Match revision and proceeds to validate the distinct complete item set with immutable definitions and file metadata; freeze item rows; set FINAL; query missing required tasks; if none insert completion and mark enrollment COMPLETED; append audit; commit. Successful retries thus do not fail merely because the original If-Match revision is now stale. First draft save/finalization sets started_at if absent and advances ENROLLED to IN_PROGRESS; finalize may then advance directly to COMPLETED in that transaction. All task finalizers lock the enrollment, including optional tasks, preventing last-two-task races. Optional tasks may be submitted later without changing the existing completion/snippet. Invalid finalization rolls back and leaves editable draft. Model answers are returned only by subsequent authorized read.

Assessment submit transaction locks attempt; checks already-SUBMITTED identical-hash replay before the stale draft revision check; otherwise validates distinct set against its pinned version, persists responses and deterministic result together and marks SUBMITTED. Repeated identical final body returns same result; changed body returns 409. Start retry uses request UUID; unlimited retakes use new UUID. No network AI dependency.

Consent revoke locks app_users, stamps revoked_at, increments privacy_version, disables relevant memory and cancels affected active runs. Dispatch and finalize recheck user privacy_version and current permissions. Bytes already sent before revocation cannot be recalled; no subsequent dispatch/read/replay is authorized after the revocation commits. Cached answers with revoked sources are withheld/redacted, not simply returned because a run was once authorized.

## 9. Structured value contracts and lifecycle precision

These contracts are implementation defaults proposed for approval, not inferred extra business capabilities. Use schemaVersion=1 for new JSON objects; reject unknown writable fields, unexpected nested objects and excess size before persistence. Legacy JSON remains unchanged in legacy tables. Defaults in this section are application-created values, not additional SQL defaults. SQL enforces object/array shape; Java validates full schemas. Canonical hashing sorts object keys and item IDs, normalizes line endings to LF, preserves meaningful Unicode/whitespace within content, uses decimal strings for IDs, UTF-8 and SHA-256. Do not hash locale-rendered UI labels or nondeterministically ordered maps.

Proposal payloads use `{schemaVersion:1,command:<typed command>}` only. CREATE_SCENARIO_DRAFT command is `{enterpriseId,slug,metadata}` with metadata fields from scenario_version excluding publication/hash/review authority; UPDATE_SCENARIO_DRAFT command is `{metadata}` applied to the bound draft; CREATE_TASK_DRAFT is `{position,title,workplaceContext,instructions,required,definitions,resources,skillIds,modelAnswer?}`; UPDATE_TASK_DRAFT has the same full task shape with existing child IDs for unchanged items, new items without IDs and explicit removed child IDs, all validated as belonging to that task. CONFIRM_EXPLORATION_PLAN is `{expectedActivePlanId,expectedRevision,title,steps}`. For all actions reject actor/status/publication/score/completion/permission fields; backend derives target ownership. Creation IDs assigned by service, not model. Structured full replacement is limited to owned draft children and requires parent revision, not generic JSON Patch.

For draft scenario/task actions, expected_revision is **scenario_version.row_version** and expected_content_hash is the canonical current draft graph hash calculated by authoring service (published-only content_hash may be NULL in draft). Every child edit increments that parent revision. For plan replacement use active plan revision/hash; for no active plan capture expectedActivePlanId=NULL and check under user lock. result_reference is `{schemaVersion:1,targetType,targetId,revision}`; stored only after successful target commit, never interpreted as unchecked dynamic table name. Executed proposal retries return this result after current actor/target access checks, before checking the old pre-execution revision or approval expiry; they never reapply the command.

Conversation GET, history context selection, run recovery and source inspector all recheck current actor/tenant and source rights. If a stored assistant message cites a now-revoked/private-inaccessible source, return a redacted/unavailable placeholder and omit it from model context; do not leak its text through durable history while denying only the chunk endpoint. User's own input remains owner-visible unless conversation context itself is no longer authorized. New memory summary is capped at 1000 characters and memory_key at 100, exact context match required. Revocation of a grant used by a proposal's source run invalidates its unexecuted PROPOSED/APPROVED proposals as STALE; manual human authoring remains possible through normal authorized commands.

KB publication captures expected knowledge_document.row_version before off-transaction work; commit locks document and verifies that revision/ownership/review is still current. A slower old ingestion cannot overwrite a newer publication. Increment document and KB revisions on publication/revoke to invalidate scoped caches. No DB lock is retained across embedding.

## 10. Deferred scope and remaining approval

Deferred: enterprise recruitment/contact workflows (scope token only), email delivery/password recovery, multi-node durable HTTP sessions, signed public certificates, certificate PDF job queues, outbox/distributed saga, ANN partitioning, generalized CMS/translations table, arbitrary tool plugins, external write connectors, skill certification, scoring of new simulations, multi-role accounts, automatic import of uncertain historical versions, vector re-embedding without approved corpus/provider use, legal deletion automation.

Session auth, retention defaults, publication gate and the one-required-task/one-required-deliverable publication defaults are proposals to approve with the whole specification. Runtime table counts, migration checksums, row anomalies, installed extension and usable credentials remain **UNVERIFIED RUNTIME ASSUMPTIONS**. Retention/deletion requirements beyond the stated proposed limits are **BLOCKED/PENDING EVIDENCE**, not an excuse to collect unrestricted data.
