AI Agent Fundamentals · Definition, Structure & Operation

AI agent = model + bộ điều phối + công cụ + ràng buộc

AI agent là một hệ thống phần mềm nhận mục tiêu, dùng model để hiểu và tạo phương án, rồi điều phối các công cụ được cấp quyền để tạo ra kết quả có thể kiểm tra. “Agent” không đồng nghĩa với “tự do hành động”: độ tự chủ được quyết định bởi harness, phạm vi tool, dữ liệu được phép và điểm cần con người xác nhận.

Chatbot và agent khác nhau ở đâu?

Question → LLM → Answer

Trọng tâm: câu trả lời có liên quan, đúng ngữ cảnh và an toàn hay không.

Chatbot có thể rất hữu ích cho hỏi đáp, tóm tắt hoặc soạn nội dung. Nó không bắt buộc phải có tool, state bền vững hay một chuỗi hành động kiểm soát.

LLM là “bộ não”, chưa phải toàn bộ agent

LLM học mẫu ngôn ngữ từ dữ liệu huấn luyện để hiểu yêu cầu và sinh nội dung. Bản thân LLM không tự có quyền đọc PostgreSQL, mở browser, gửi email hay ghi file. Muốn tác động ra bên ngoài, hệ thống phải cung cấp tool và code gọi tool.

Internet cũng không tự làm model “thông minh hơn”. Web search hoặc API chỉ là một tool để lấy dữ liệu mới; harness phải giới hạn nguồn, kiểm tra kết quả và quyết định dữ liệu nào được đưa trở lại model.

Cấu tạo chung: mỗi thành phần trả lời một câu hỏi kỹ thuật

1 · LLM / model

Hiểu ý định, tổng hợp lập luận và diễn đạt. Ví dụ: Gemini, GPT, Claude hoặc một model nội bộ.

2 · Harness

“Hệ thần kinh” bằng code: ghép prompt, context, retry, quan sát tool result, điều kiện dừng, log và đánh giá.

3 · Tools

“Tay chân”: hàm/API có schema rõ ràng như đọc evidence, tìm resource đã duyệt, tạo plan draft; không phải quyền vô hạn.

4 · Context & memory

Thông tin được phép dùng ngay lúc này và summary của phiên trước. Memory phải có owner, thời hạn, kích thước và nút xóa.

5 · Orchestrator

Chạy workflow: nạp state → policy/planning → tool → model (nếu cần) → validate → response/persist.

6 · Guardrails

Authentication/ownership, allowlist, consent, input boundary, JSON schema, timeout, rate limit và human confirmation.

Một vòng hoạt động của agent

Một agent có thể lặp lại vòng này nhiều lần, nhưng chỉ khi harness cho phép. Với các hành động có tác động dữ liệu hoặc chi phí cao, agent nên dừng để xin xác nhận thay vì tự tiếp tục.

Phân loại theo phạm vi hành động, không theo tên marketing

Type A

Conversational assistant — một lượt prompt → text; ví dụ ChatGPT, Gemini hoặc Claude ở chế độ chat thông thường.

Text response
Type B

Grounded / retrieval assistant — trả lời từ knowledge base, document hoặc search có kiểm soát; ví dụ agent được cấu hình knowledge trong Microsoft Copilot Studio.

Context retrieval
Type C

Workflow / bounded agent — server xác định tool, thứ tự và dữ liệu; ví dụ form/service agent, GitHub Copilot coding agent trong phạm vi repository được cấp.

Controlled actions
Type D

Stateful bounded agent — thêm goal, session memory, observations và human confirmation cho write action. Đây là phân loại phù hợp với Syn.

Syn hiện tại
Type E

Autonomous / multi-agent — planning nhiều vòng, có thể phân công agent con; ví dụ coding/research environment như Claude Code hoặc Codex khi được cấp tool environment rộng.

Higher risk & cost

Các sản phẩm trên là ví dụ định hướng; năng lực và quyền của từng sản phẩm phụ thuộc phiên bản, cấu hình tool, account và policy triển khai. CareerSim không phụ thuộc vào chúng. Tham khảo chính thức: Microsoft Copilot Studio, GitHub Copilot và Claude Code.

Syn Agent · Evidence-grounded, bounded and human-in-the-loop

Syn không chỉ trả lời: Syn điều phối exploration workflow có giới hạn

Syn hỗ trợ sinh viên kết nối RIASEC với trải nghiệm simulation, nhận ra evidence còn thiếu, so sánh hướng đi, tìm reviewed resource/simulation và tạo plan draft. Syn không chọn nghề thay người dùng, không chấm điểm bằng AI và không tự lưu thay đổi.

Điểm khác so với prototype: Syn không còn lấy toàn bộ evidence rồi gọi model để trả text. Phiên bản hiện tại chọn intent, active evidence và tool plan bằng backend policy trước; Gemini chỉ tổng hợp ngôn ngữ từ context đã được thu hẹp và kiểm tra.

Syn đang làm được gì cho sinh viên?

Khởi động cho người mới

Nhận diện tình huống chưa có evidence và chuyển sang GET_STARTED: giới thiệu các IT path và simulation công khai để bắt đầu trải nghiệm, không suy đoán “phù hợp nghề nào”.

Đọc đúng evidence được hỏi

Ưu tiên attempt mà sinh viên chọn, path được nhắc trong câu hỏi hoặc path trong session; chỉ dùng latest result khi intent thực sự là xem kết quả gần nhất.

So sánh exploration paths

Tạo comparison card và evidence/result cards cho các path được nêu rõ, ví dụ Frontend và Backend, rồi gợi ý một thử nghiệm tiếp theo thay vì kết luận nghề nghiệp.

Tìm resource đã rà soát

Toolbox trả resource card có provider, URL, skill, độ khó và thời lượng. Model chỉ giải thích từ card này, không tự bịa link hay duyệt web không giới hạn.

Plan có con người kiểm soát

Syn tạo draft, UI yêu cầu người dùng review và Confirm & save. Chỉ API lưu plan thành công mới ghi PostgreSQL.

Hội thoại có continuity

Nhớ ngôn ngữ, stage, topic/path đã xét và next action dưới dạng summary giới hạn 30 ngày; transcript hiển thị chỉ là sessionStorage của tab và có nút xóa.

Tạo Syn từ một chatbot: 6 quyết định kỹ thuật

Bấm từng bước. Đây là thứ tự triển khai đúng với mã nguồn CareerSim, không phải pseudo-agent chung chung.

Luồng thật khi sinh viên gửi một câu hỏi tự do

React SynWidget
  → POST /v1/guidance/syn/messages
  → GuidanceServiceImpl: active student + selected attempt ownership
  → SynAgentOrchestrator: session → policy → toolbox → optional provider
  → SynMessageResponse: text + provenance + cards + suggestions + plan draft
  → React renders response progressively; user confirms any write action

Đây là ranh giới trách nhiệm quan trọng: frontend không gọi Gemini trực tiếp; provider không truy cập database; LLM không tự chọn SQL/tool; các score khách quan vẫn do assessment/simulation evaluator quyết định.

Evidence selection: chống “lấy nhầm latest result”

  1. Attempt mà sinh viên bấm View with Syn.
  2. Path/result được nhắc rõ trong câu hỏi.
  3. Path đang so sánh hoặc được nhớ trong structured session.
  4. Latest result chỉ khi intent thực sự là review latest.

So sánh FE/BE chỉ trả evidence/result cards của Frontend và Backend; attempt cùng path được deduplicate theo kết quả mới nhất.

Memory và transcript là hai thứ khác nhau

Server memory là summary có cấu trúc, owner-scoped và hết hạn 30 ngày: ngôn ngữ, stage, current goal, covered topics, considered paths và next action. Nó không lưu raw transcript.

v=2 | lang=VI | stage=PLANNING | covered=COMPARE_PATHS | next=TRY_COMPARISON_SIMULATION

Visible chat được giữ tạm trong sessionStorage của tab, tối đa 24 message. Thu nhỏ popup hoặc đổi route không xóa; chỉ thùng rác mới xóa transcript UI và yêu cầu backend xóa session memory.

Syn được phép

Đọc evidence thuộc student, giải thích RIASEC, review result cụ thể, so sánh path, tìm evidence gap, đề xuất published simulation/reviewed resource, draft plan và trả lời EN/VI.

Syn không được phép

Query SQL tùy ý, đọc dữ liệu người khác, duyệt web không giới hạn, đổi score, chấm bài bằng AI, tự lưu plan, cấp chứng nhận hay chọn nghề thay sinh viên.

Vì sao đây là agent nhưng chưa autonomous?
Syn có state, memory, intent routing, tool plan, observation, next-action proposal và fallback. Tuy nhiên backend policy—not the LLM—chọn tool; provider không truy cập PostgreSQL; một lượt free-text tối đa một provider call; và ghi dữ liệu cần confirmation. Đây là trade-off chủ động để giảm token, hallucination và rủi ro dữ liệu sinh viên.

Security Architecture · Defense in Depth

Bảo mật Đa tầng (Defense-in-Depth)

Hệ thống áp dụng cơ chế bảo mật nhiều lớp từ Nginx Edge Gateway tới Spring Security và Database Invariants.

01 · Nginx Edge Limits

Giới hạn Syn Rate Limit 10 req/phút/IP, Body size tối đa 16 KiB, Read timeout 15s. Áp dụng Security Headers: CSP, Frame-Options DENY, X-Content-Type-Options.

02 · Role & State Control

Phân quyền nghiêm ngặt (STUDENT, ENTERPRISE, ADMINISTRATOR). Sinh viên chỉ có quyền xem dữ liệu của chính mình. Account bị LOCKED/INACTIVE bị từ chối truy cập.

03 · Secret Isolation

API Keys (Gemini/OpenAI) chỉ nằm tại biến môi trường Backend (.env). Tuyệt đối không chứa tiền tố VITE_, không rò rỉ vào Frontend bundle hay Git repository.

04 · Schema Validation

Message tối đa 600 ký tự. Phản hồi AI bắt buộc tuân thủ JSON Schema định sẵn (text + tối đa 3 suggestions). Mọi output sai cấu trúc bị hủy và chuyển sang Fallback.

05 · Audit Provenance

Bảng guidance_reports ghi lại nguồn gốc đầy đủ: AI hoặc FALLBACK/STANDARD, Model Name, Generation Latency (ms), Audit Status.

06 · Prompt Boundary

Phát hiện và vô hiệu hóa các câu lệnh Jailbreak/Prompt Injection (yêu cầu tiết lộ System Prompt, phán quyết nghề nghiệp cố định, cam kết việc làm...) ngay trước khi gọi External LLM.

AI-Assisted Workflow · Traceability Chain

Quy trình Phối hợp & Kiểm soát AI Agent trong Dự án

AI Agent hỗ trợ phát triển code và lên kế hoạch, nhưng Nhóm phát triển giữ quyền kiểm soát tuyệt đối thông qua Chuỗi truy vết (Traceability Chain) và Quality Gates bắt buộc.

Chuỗi Truy Vết Bắt Buộc (Traceability Chain):
Proposal / SRS → User Story → Acceptance Criteria → Feature Plan (plans/) → Code → Tests → Evidence (reports/ + command output)

1. Lên Kế Hoạch Trước Khi Code

Trước khi sửa bất kỳ dòng code nào, AI đọc AGENTS.md, copy template và tạo bản kế hoạch plans/US-XX-short-name.md làm rõ Actor, Flows, Boundary và Security Impact.

2. Kiểm Soát Kiến Trúc Đặt Ra

Tuân thủ nghiêm ngặt Modular Monolith. Controller không chứa Business Rules, ServiceFacade giấu Transaction, Domain Entities giữ Invariants, DAO chỉ làm nhiệm vụ Persistence.

3. Quality Gates Thực Xem Bằng Chứng

Không chấp nhận báo cáo hoàn thành nếu chưa chạy lệnh kiểm thử thực tế (mvnw verify, npm run check, docker compose config) và đối soát log thực chứng.

.agent là context có kiểm soát, không phải “prompt dài”

Trước khi thay đổi, coding agent đọc AGENTS.md, PROJECT_CONTEXT.md, TASKS.md, DESIGN.md và rules. Các file này đóng gói scope, business rules, owner boundary, security/privacy, testing gates và reporting discipline thành context thường trực.

Với US-03, các constraint được giữ xuyên suốt là: exploration—not career prediction; score deterministic; LLM không truy cập DB; fallback bắt buộc; plan cần confirmation; và evidence chỉ thuộc student hiện tại.

Cách dùng AI để truy vết, sau đó kiểm chứng độc lập

Có thể hỏi coding agent: “Request này đi qua file nào?”, “Rule này được test ở đâu?”, “Migration nào tạo field này?”, hoặc “Tài liệu có lệch code không?”. Nhưng câu trả lời chưa phải evidence.

Nhóm đối chiếu bằng rg/Git diff, unit test, Testcontainers integration, API response thật, Docker gateway và browser flow. AI tạo/tìm nhanh; human review quyết định có merge hay không.

Quality-control loop: AI đề xuất → Human review scope → compile/lint → unit test → integration test → security/secret review → Docker smoke → manual UI verification → docs/evidence update → commit có trace. Không dùng AI để thay thế kiểm soát chất lượng; dùng AI để tăng tốc cả implementation lẫn truy vết sai lệch.

Hướng dẫn Cấu hình, Chạy & Kiểm thử Fallback

Mọi cấu hình nhạy cảm chỉ nằm tại file .env ở root dự án (đã git-ignore). Dưới đây là các bước khởi động và kiểm chứng toàn stack.

1. Cấu hình biến môi trường (.env) — Bật Gemini & Local Demo 
AI_PROVIDER=gemini
GEMINI_API_KEY=YOUR_PRIVATE_GEMINI_KEY
GEMINI_MODEL=gemini-3.5-flash-lite
LOCAL_DEMO_MODE=true
LOCAL_DEMO_EMAIL=student@demo.com
2. Khởi chạy Services bằng Docker Compose (Hoặc Triển khai trên Ubuntu VM) 
docker compose up -d --build
docker compose ps
Invoke-RestMethod -Uri "http://localhost:8080/api/health"
3. Kiểm tra dữ liệu và AI consent của Student Demo do Flyway V8 tạo 
docker compose exec -T postgres psql -U career_sim -d career_simulation -c \
"SELECT u.email, p.consented_to_ai_at FROM app_users u \
 JOIN student_profiles p ON p.user_id = u.id WHERE u.email = 'student@demo.com';"
4. Lệnh chạy Automated Quality Gates (Backend Verification & Frontend Lint/Build) 
# Run Backend Quality Gates
cd backend
.\mvnw.cmd verify

# Run Frontend Quality Gates
cd ..\frontend
npm run check
